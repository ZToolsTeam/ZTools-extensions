# 界面规范

ZTools 是「呼出即用、用完即走」的效率工具：用户按下快捷键，几秒内找到目标、按一下回车就走。插件界面要服务这个目标，而不是做成功能齐全的后台管理页面。

本文是插件界面的完整规则，审核按它把关。前面四节讲规则，后面三节是写代码和提交前对照用的：

1. [组件与键盘约定](#组件与键盘约定)
2. [八条原则](#八条原则)
3. [三种标准布局](#三种标准布局)
4. [选择布局](#选择布局)
5. [属性约定](#属性约定)
6. [提交前自检](#提交前自检)
7. [扫描器提示对照](#扫描器提示对照)

组件和属性的完整说明见 [API 参考](api.md)。

## 组件与键盘约定

插件只能用 `@ztools/declarative-ui` 提供的组件描述界面：`List`（含 `List.Item`、`List.Section`、`List.Dropdown`）、`Detail`（含 `Detail.Metadata`）、`Form`（含 `TextField`、`TextArea`、`Checkbox`、`Dropdown` 等）、`ActionPanel` 和 `Action`。插件不写 HTML、不操作 DOM、不写 CSS；配色、字体、深浅主题和动画都由客户端统一处理。

客户端为所有插件提供同一套键盘操作，插件不需要自己实现：

| 按键 | 作用 |
| --- | --- |
| `↑` / `↓` | 在列表中移动选中项 |
| `Enter` | 执行选中项的第 1 个动作（主动作） |
| `⌘/Ctrl+Enter` | 执行第 2 个动作（次动作）；在表单里是提交 |
| `⌘/Ctrl+K` | 打开动作面板，列出全部动作 |
| `Esc` | 关闭动作面板 → 返回上一页 → 清空搜索 → 退出插件 |
| `Space` | 搜索框为空或焦点在列表上时，勾选 / 取消勾选当前行（可勾选列表） |
| `←` / `→` | 布局二里在左侧导航和右侧明细之间切换（焦点不在输入框时） |

本文写作 `⌘/Ctrl` 的按键，在 macOS 上是 `⌘`，在 Windows 上是 `Ctrl`。给动作声明快捷键时也一样：`shortcut: { modifiers: ["cmd"], key: "r" }` 在 macOS 上对应 `⌘R`，在 Windows 上对应 `Ctrl+R`，写 `"ctrl"` 效果相同。

## 八条原则

### 原则 0：先想清楚对用户有什么用

加任何组件、按钮、统计数字或交互步骤之前，先回答三个问题：它对用户有什么用？解决了什么具体问题？不加的话，用户的主要任务会受阻吗？

不能帮用户「更快找到目标、更准做出判断、更少按键完成操作」的元素一律不加。不要为了让界面看起来丰富而堆东西。

### 原则 1：大部分空间留给列表或主工作区

用户打开插件，是为了找到并操作某一条内容，不是看报表。

- 顶部只放搜索框，以及最多一行状态条（`filterBar.summaryText`）。
- 不在列表上方堆统计卡片、多行筛选标签或大段说明。
- 首屏应该能完整看到 7~10 行列表内容。

### 原则 2：同一个功能只出现一次

- **筛选入口只有一个**：搜索框右侧已经有下拉筛选（`List.Dropdown`），就不要在下面再放一排同样维度的筛选标签（`filterBar.groups`）；左侧已经有分类导航，就不要再放彩色比例条。
- **动作只出现在一个地方**：同一个操作不要同时出现在顶栏、列表行里、详情区和底部。

### 原则 3：全局动作和单条动作分开

- **顶部状态条**：左边一句话说明当前状态（可以带关键数字），右边最多放 1~2 个针对整个插件的按钮，比如「新建」「重新扫描」。
- **针对选中项的操作**（删除、结束进程、复制、定位……）一律放进选中项的 `ActionPanel`，由客户端显示在底部操作栏：主动作（`Enter`）、次动作（`⌘/Ctrl+Enter`）、动作面板（`⌘/Ctrl+K`）。不要把这类按钮放到顶部状态条。
- 列表行右侧只放状态信息（`accessories`：标签、进度、数值），不放按钮。

### 原则 4：常用的直接给，不常用的收起来

底部只直接显示最常用的两个动作：第 1 个（`Enter`）和第 2 个（`⌘/Ctrl+Enter`）。第 3 个及以后的动作自动收进 `⌘/Ctrl+K` 动作面板。常用但排在后面的动作可以声明 `shortcut`，用户不打开面板也能直接触发。

所以 `ActionPanel` 里动作的顺序要按使用频率排：最常用的放第一个。

### 原则 5：灰阶为主，不用彩色 Emoji

- **不用彩色 Emoji**：标题、状态条、下拉选项、按钮文字里都不要出现 Emoji（它们在 Windows 上会显示成高饱和的彩色图块）。图标统一用 `Icon.*` 单色图标。
- **不给同类条目上不同颜色**：列表图标、标签保持默认的灰阶，不要给每一行循环配紫、蓝、绿、黄等没有含义的颜色。进度条只靠长度体现差异。
- **颜色只用来表示风险**：只有真正需要警示的情况（例如磁盘使用超过 90%）才给标签或数值加 `color: Color.Red`。
- 强调色由客户端统一用在主动作按钮和当前选中项上，插件不需要也不应该自己设置。

### 原则 6：只用三种标准布局

所有带界面的插件都从下一节的三种布局里选一种，不要自己发明第四种。没有界面的命令用 `no-view` 模式。

### 原则 7：先选布局，再写代码

动手前按 [选择布局](#选择布局) 的问题逐条判断，确定布局后从对应的示例插件开始改。

## 三种标准布局

下面的示意图里，第 1 层（搜索框）和第 4 层（底部操作栏）由客户端统一绘制，插件只提供内容。

### 布局一：单栏列表（可带右侧内容预览）

适合：检索、切换、系统状态、开关集合、剪贴板、词典这类「找到一条 → 执行」的插件，大多数插件都属于这一种。

```text
+-----------------------------------------------------------------------------------+
| 搜索框                                            [分类 / 排序下拉框 ▾]           | <- 第 1 层：搜索与唯一的筛选入口
+-----------------------------------------------------------------------------------+
| 一句话状态摘要（可带关键数字）                              [新建 / 刷新]（全局） | <- 第 2 层：单行状态条（可省略）
+-----------------------------------------------------------------------------------+
| 选中项标题  副标题（完整路径 / PID / 端口）          [指标标签] [状态标签]         |
| 普通项标题  副标题                                   [指标标签] [状态标签]         | <- 第 3 层：全宽列表
| 普通项标题  副标题                                   [指标标签] [状态标签]         |    （或左侧列表 + 右侧真实内容预览）
+-----------------------------------------------------------------------------------+
| Esc 返回                                  | [主动作 ↵]  [次动作 ⌘↵]  [动作面板 ⌘K]  | <- 第 4 层：底部操作栏
+-----------------------------------------------------------------------------------+
```

- 一行（标题 + 副标题 + 右侧标签）就能说清楚的，用**全宽列表**：`isShowingDetail={false}`。
- 只有右侧要显示的是**内容本身**（剪贴板里的长文本、代码片段、词典释义、二维码图片、硬件参数表）时，才打开右侧预览：`isShowingDetail={true}`，给每个 `List.Item` 传 `detail`。不要为了凑成两栏，在右侧重复列表里已有的标题和路径。
- 只有几个开关或快捷动作的轻量插件，可以不传 `filterBar`，界面就是「搜索框 + 列表 + 底部操作栏」。

示例：

| 插件 | 平台 | 看点 |
| --- | --- | --- |
| [`process-monitor`](../extensions/process-monitor/src/index.ts) | 跨平台 | 全宽列表 + 单行状态条 |
| [`clipboard-manager`](../extensions/clipboard-manager/src/index.tsx) | 跨平台 | 右侧预览剪贴板内容本身 |
| [`kill-process`](../extensions/kill-process/src/index.tsx) | 仅 Windows | 下拉筛选 + 状态条 + 结束进程动作 |

### 布局二：左侧导航 + 右侧可勾选明细

适合：「左边选一个分类 / 磁盘 / 账号 / 数据表 → 右边列出成百上千条明细 → 勾选后批量清理、卸载、移动」这类一对多的管理和清理插件。

```text
+-----------------------------------------------------------------------------------+
| 搜索大文件、后缀或路径...                         [全部磁盘 / 账号切换 ▾]         | <- 第 1 层：搜索与数据源切换
+-----------------------------------------------------------------------------------+
| 总容量 1.7 TB / 已用 1.3 TB (78%) · 右侧共 678 项                    [重新扫描]   | <- 第 2 层：单行状态条
+--------------------------+--------------------------------------------------------+
| 分区 / 分类导航（约 32%）| [ ] 可清理的大文件（按体积降序，勾选或按 ↵）           |
| > 全部大文件       678项 | [✓] Windows11_x64.iso        █████░░ [镜像]    8.0 GB  |
| > 系统分区 (C:)     98%  | [ ] Ubuntu-Snapshot.vmem     ████░░░ [其他]    8.0 GB  | <- 第 3 层：左侧导航 + 右侧明细（约 68%）
| > 数据库与资源包  67.7GB | [锁] pagefile.sys            ███░░░░ [系统保护] 4.0 GB  |
+--------------------------+--------------------------------------------------------+
| Esc 返回                 | [移到回收站 ↵]    [在文件管理器中显示 ⌘↵]    [⌘K]      | <- 第 4 层：底部操作栏
+--------------------------+--------------------------------------------------------+
```

- 用 `<List isShowingDetail={false} subList={...}>` 实现：`List` 的子元素 `List.Item` 是左侧导航节点，`subList.items` 是右侧明细行。导航节点被选中时（`List.Item` 的 `onSelect`，或 `List` 的 `onSelectionChange`），插件更新状态，换成这个节点对应的明细。
- 右侧明细行用 `checkable` / `checked` / `onCheckChange` 支持勾选，`subList` 本身的 `checkable` / `checked` 控制表头的全选框。
- 行右侧用 `accessories` 放单色进度条（体积占比）、中性标签和数值。
- 底部操作栏的动作作用于右侧选中项或已勾选的集合。

示例：

| 插件 | 平台 | 看点 |
| --- | --- | --- |
| [`disk-analyzer`](../extensions/disk-analyzer/src/index.ts) | 跨平台 | 分区 / 分类导航 + 可勾选的大文件明细 |
| [`batch-rename`](../extensions/batch-rename/src/index.ts) | 跨平台 | 左侧目录 + 右侧待重命名文件 |

### 布局三：左侧参数 + 右侧任务队列

适合：批量转码、批量处理音频、PDF 处理、OCR、截图、录屏这类「左边设定处理参数 → 右边看待处理队列和预计结果 → 一键开始」的插件。

```text
+-----------------------------------------------------------------------------------+
| 搜索队列文件...                                   [预设方案：画质压缩 ▾]          | <- 第 1 层：搜索与预设切换
+-----------------------------------------------------------------------------------+
| 已选 36 个视频 (1.4 GB) · 预计转码后约 476 MB（节省 66%）            [重新扫描]   | <- 第 2 层：任务预估状态条
+----------------------------+------------------------------------------------------+
| 转码参数（约 34%）          | [✓] 待处理视频（约 66%）                             |
| 输出格式  [ MP4      ▾]    | [✓] 演示录屏_01.mov        █████░░ [→ 约 30MB] 89.5 MB |
| 视频编码  [ H.265    ▾]    | [✓] 会议录像_1018.mp4      ████░░░ [→ 约 29MB] 85.2 MB | <- 第 3 层：左侧参数 + 右侧队列
| 画质      [ CRF 23   ▾]    | [✓] 产品宣传_4K.mp4        ███░░░░ [→ 约 26MB] 78.9 MB |
| 预计节省：约 924 MB         |                                                      |
+----------------------------+------------------------------------------------------+
| Esc 返回                   | [开始批量转码 ↵]      [打开输出目录 ⌘↵]      [⌘K]   | <- 第 4 层：底部操作栏
+----------------------------+------------------------------------------------------+
```

- 用 `<List isShowingDetail={false} workbenchPanel={...} subList={...}>` 实现：`workbenchPanel.fields` 是左侧参数（`select` / `toggle` / `text` / `info`），`workbenchPanel.previewCard` 是一张简短的预估摘要；`subList` 是右侧可勾选的处理队列。
- 底部主动作通常是「开始处理」，次动作是「打开输出目录」。

示例：

| 插件 | 平台 | 看点 |
| --- | --- | --- |
| [`screenshot`](../extensions/screenshot/src/index.tsx) | 跨平台 | 左侧截取选项 + 右侧可勾选的截图列表 |
| [`batch-video`](../extensions/batch-video/src/index.ts) | 仅 Windows | 转码参数 + 待转码队列与预计大小 |

### 表单与详情页

新建 / 编辑配置这类二级页面用 `Form`，纯阅读的结果页用 `Detail`（Markdown 正文，可选右侧 `Detail.Metadata` 属性栏）。它们和三种布局共用同一套顶部和底部，通常由列表里的 `Action.Push` 打开，`Esc` 返回。

## 选择布局

按顺序回答下面的问题，第一个回答「是」的就是你的选择。

**问 0：用户触发后，是否根本不用看列表、不用选择，执行一个动作就结束？**（例如锁屏、切换深浅色、生成 UUID 写入剪贴板、复制当前时间戳）

是 → 用**无界面命令**：`plugin.json` 里写 `"mode": "no-view"`，默认导出一个异步函数，不渲染任何 `List` / `Detail` / `Form`。用户在搜索框里选中它回车就执行，函数返回的字符串会作为结果提示显示，抛出错误则显示为执行失败：

```ts
import { Clipboard } from "@ztools/declarative-ui";

export default async function Command() {
  const value = String(Date.now());
  await Clipboard.copy(value); // 写入失败会抛错，客户端提示执行失败
  return `已复制 ${value}`;
}
```

**问 1：用户是否要先在左边设定一组处理参数（格式、画质、倍率、识别语言、命名规则），同时在右边看待处理队列和预计结果？**

是 → **布局三**。

**问 2：数据是否是「左边分类 / 磁盘 / 账号 / 数据表 → 右边大量可勾选明细，批量处理」的一对多关系？**

是 → **布局二**。

**问 3：是否是新建 / 编辑配置的二级页面，或者只读的单篇结果？**

是 → `Form` 或 `Detail`。

**其他所有带界面的情况** → **布局一**，再按内容选一种写法：

| 情况 | 写法 |
| --- | --- |
| 几个开关或快捷动作 | 不传 `filterBar`，`isShowingDetail={false}` |
| 检索、监控类（进程、端口、窗口） | 传单行 `filterBar={{ summaryText, actions }}`，`isShowingDetail={false}` |
| 右侧要看内容本身（长文本、释义、图片） | `isShowingDetail={true}`，右侧只放内容本身 |

## 属性约定

| 位置 | 写法 |
| --- | --- |
| 搜索框右侧的筛选 / 排序 / 数据源切换 | `searchBarAccessory={<List.Dropdown value={...} onChange={...}>…</List.Dropdown>}` |
| 第 2 层单行状态条 | `filterBar={{ summaryText: "一句话摘要", actions: [{ id: "rescan", title: "重新扫描", onAction }] }}`，`actions` 最多 2 个；轻量插件不传 |
| 列表行右侧信息 | `accessories={[{ progress: 0.65 }, { tag: "镜像" }, { text: "8.0 GB" }]}`，不传 `color`；只有高危告警（如超过 90%）可以传 `color: Color.Red` |
| 底部操作栏 | 在选中项（或 `subList` 明细行）的 `actions` 里放 `<ActionPanel>`：第 1 个 `Action` 是主动作（`Enter`），第 2 个是次动作（`⌘/Ctrl+Enter`），其余进动作面板（`⌘/Ctrl+K`） |

SDK 类型里还能看到下面这些属性和组件，它们是历史遗留，**不要使用**，扫描器会给出提示：

| 类型里有的 | 为什么不用 | 改成 |
| --- | --- | --- |
| `metricGrid` 属性、`MetricGrid` / `MetricCard` 组件 | 列表上方的统计卡片挤占列表空间（原则 1） | 把关键数字写进 `filterBar.summaryText` |
| `distributionBar` 属性、`DistributionBar` 组件 | 彩色比例条与分类导航重复，而且是彩色（原则 2、5） | 左侧导航节点的 `accessories` 写数量或占比 |
| `filterBar.groups`（同时有 `searchBarAccessory` 或左侧导航时） | 和下拉筛选或导航重复（原则 2） | 只保留一个筛选入口 |

## 提交前自检

提交前逐条确认，任何一条答「是」都要改：

1. 是否自己发明了第四种布局，或者写了 HTML / CSS、直接操作了 DOM？
2. 是否在列表上方放了统计卡片（`metricGrid` / `MetricGrid`）或彩色比例条（`distributionBar`）？
3. 已经有搜索框右侧的下拉筛选或左侧导航，是否又传了 `filterBar.groups`？
4. 标题、状态条、选项、按钮文字里是否有彩色 Emoji？
5. 是否给普通列表图标或标签配了没有含义的彩色（`Color.Blue`、`Color.Green` 等）？
6. 开了 `isShowingDetail={true}` 时，右侧是否只是重复了列表行里已有的标题和路径？（是的话改成全宽列表）

第 2~5 条扫描器能部分发现（见下一节），第 1 条里的「第四种布局」和第 6 条只能靠审核人员看，扫描通过不代表没问题。

## 扫描器提示对照

运行 `node scripts/scan-plugin-security.mjs extensions/<id>` 时，界面相关的结果如下。`UI_*` 是提示（warning），不会让扫描失败，但审核时会按本规范要求修改；其余三项是错误，扫描直接不通过。

| 编号 | 级别 | 含义 | 对应规则 | 怎么改 |
| --- | --- | --- | --- | --- |
| `UI_COLORFUL_EMOJI` | 提示 | 源码里出现了彩色 Emoji | 原则 5、自检第 4 条 | 删掉 Emoji，需要图标时用 `Icon.*` |
| `UI_METRIC_GRID` | 提示 | 用了 `MetricGrid` / `metricGrid` | 原则 1、自检第 2 条 | 关键数字并入 `filterBar.summaryText` |
| `UI_DISTRIBUTION_BAR` | 提示 | 用了 `DistributionBar` / `distributionBar` | 原则 2、5，自检第 2 条 | 去掉比例条，用导航节点的 `accessories` 表达 |
| `UI_RAINBOW_COLOR` | 提示 | `color` / `tintColor` 用了 `Color.Blue`、`Green`、`Orange`、`Purple`、`Yellow`、`Magenta` | 原则 5、自检第 5 条 | 去掉颜色；只有高危告警可用 `Color.Red` |
| `UI_DUPLICATE_FILTER` | 提示 | 同一文件里既有 `searchBarAccessory`，又有 `filterBar.groups` | 原则 2、自检第 3 条 | 只保留一个筛选入口 |
| `DISALLOWED_STYLE_FILE` | 错误 | 插件目录里有 `.css` / `.less` / `.scss` / `.sass` / `.styl` 文件 | 自检第 1 条 | 删除样式文件，界面只用组件描述 |
| `DISALLOWED_INLINE_STYLE` | 错误 | HTML 文件里有 `<style>` 标签或 `style="..."` 属性 | 自检第 1 条 | 不用 HTML，改用组件 |
| `DISALLOWED_DOM_STYLE_INJECTION` | 错误 | 代码里用 `document.createElement('style' / 'link')`、改元素的 `style`，或用 `innerHTML` 注入 `<style>` | 自检第 1 条 | 删掉这些代码，样式交给客户端 |

扫描器的安全类规则（`eval`、混淆、未声明权限等）见 [审核标准 · 扫描规则](review.md#扫描规则)。
